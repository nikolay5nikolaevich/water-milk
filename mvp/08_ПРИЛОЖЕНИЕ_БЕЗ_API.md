# Реализованный сценарий: amoCRM и ИИ по подписке

Актуальное решение от 03.11.2026: локальное приложение, чтение сделок и переписок amoCRM и автоматическая оценка кнопкой «Проверить ответ менеджера» через Codex с входом по подписке ChatGPT. API-ключ модели и ручной перенос JSON не нужны. Оно расширяет первоначальный документальный MVP. Данные в amoCRM приложение не изменяет.

## Конечный результат

- Дашборд: число диалогов, средний подтверждённый балл, критические сигналы и очередь проверки. Учебная и рабочая выборки отделены.
- Карточка: история сообщений, вопросы клиента, оценки пяти критериев, доказательства, исправленный ответ и обратная связь.
- База: ID правила, текст, источник, владелец, статус и даты действия. Импорт/редактирование JSON; копия активной базы в каждом разборе.
- Работа через подписку: нажать «Проверить ответ менеджера»; приложение формирует задание, запускает Codex CLI, проверяет доказательства и сохраняет результат. Ручной импорт остаётся дополнительным вариантом.
- Журнал решений проверяющего, история результатов, CSV и JSON для выгрузки.

## Как реализована «нейронка, которая ссылается на правила»

В MVP используется готовая модель через официальный Codex CLI с авторизацией ChatGPT. Дообучать свою модель не нужно. Приложение формирует контекст из правил, действовавших на дату переписки, и рубрики QA-DEMO-1.0. Эталоны в задание не передаются. `codex exec` получает JSON Schema; shell, приложения, браузер, плагины и хуки для проверки отключены, API-ключи исключены из окружения. Модель получает диалог и правила по stdin.

На небольшой базе передаётся весь применимый набор правил: это позволяет не потерять важное ограничение при поиске. Векторная база и embeddings для текущего объёма не требуются. Если база вырастет, можно добавить поиск фрагментов, сохранив обязательную передачу общих регламентов, ID и версий; это ещё не реализовано.

Модель возвращает JSON с полями:

- `dialogue_id`, `input_hash`, `kb_version`, `kb_hash`, `rubric_version` — привязка к входным данным;
- `questions` — вопросы клиента, ссылки на ответы и статус;
- `scores` — пять критериев с баллами и объяснениями;
- `findings` — criterion, kind, message_id, quote, rule_ids, explanation;
- `strengths`, `feedback`, `corrected_reply` — обратная связь;
- `missing_context`, `kb_proposals` — недостающие данные и черновики предложений.

Для каждого снижения балла нужно замечание с существующей цитатой и активным правилом. Итог вычисляет приложение, а не модель. Для Н/Д используется JSON `null`; общий балл при этом отсутствует. Установлены отдельные ограничения для неполной истории и пустого контекста карточки.

Проверка формата и ссылок детерминирована. Проверка смысла остаётся за человеком: наличие цитаты само по себе не доказывает нарушение. Хеши связывают ответ с версией входа, но не удостоверяют автора ответа. Импортированный JSON помечается как «ответ из чата» по действию пользователя, приложение не может установить, какая модель его создала.

## Реальный рабочий цикл

1. Подключают amoCRM, выбирают сделки и импортируют найденные переписки из примечаний. Для остальных источников остаётся ручной ввод. Перед передачей в ИИ данные обезличивают.
2. Указывают дату, полноту и контекст карточки. Автор менеджера сохраняется в каждом сообщении.
3. Приложение исключает черновики, архив и правила вне периода действия.
4. Нажимают кнопку проверки. Приложение использует существующий локальный вход Codex через ChatGPT. При отсутствии входа показывает команду входа; автоматической подмены на API-ключ нет.
5. Ответ получается и проверяется автоматически. При ошибке доказательств допускается одна попытка исправления; неподтверждённый результат не сохраняется как успешный. При лимите подписки или ошибке входа показывается причина.
6. Проверяющий сверяет смысл, отмечает решение и обоснование. Спорный ответ сохраняется без редактирования под эталон; новую версию ответа импортируют отдельным результатом.
7. Последний подтверждённый результат каждого диалога может войти в средний балл. Если последний результат спорный или ещё не проверен, старое подтверждение не переносится на него автоматически.

## Границы готовности

Приложение и автоматические проверки работают локально. Встроенные D01–D05 содержат авторские эталоны из файла 04; загрузка примера не является прогоном нейросети.

Реализовано чтение сделок, ответственных, этапов и примечаний по API amoCRM, предпросмотр и импорт выбранных переписок с явными ролями. История чатов отдельных каналов требует отдельной интеграции; наличие беседы не выдаётся за доступ к её сообщениям. Подробности подключения — в README.

Для стандартного Telegram-бота добавлен экспериментальный браузерный читатель: отдельный Chrome с входом пользователя, перехват ответов истории только выбранных chat_id, проверка авторства по `amojo_id`, предпросмотр, выбор режима и явное подтверждение полноты. Пароли, токены и заголовки ответов в набор переписки не копируются. Публичный стабильный доступ к истории встроенного Telegram по одному CRM-токену не заявляется. На живом аккаунте этот путь ещё нужно проверить. Оценка через модель по-прежнему выполняется отдельно после загрузки текста.

Последующая живая проверка выявила фактический путь `/ajax/v3/leads/{id}/events_timeline` и сообщения, привязанные к контакту. Читатель исправлен; повторное чтение из CRM вернуло 4 сообщения, сохранение и отображение этой переписки в работающем приложении проверены. Общая полнота истории и оценка ИИ этим не подтверждаются. В интерфейс добавлены этап загрузки, число ответов и HTTP-статус вместо необъяснённого нуля.

Автоматическая оценка реально выполнена через подписку Codex на импортированной переписке. Поскольку правила компании отсутствуют, используется явно обозначенная общая рубрика GENERAL-QA-1.0: цены, сроки и регламент не оцениваются как подтверждённые факты и остаются Н/Д. Фрагментарная история не получает выдуманного общего балла.

Для подтверждённых пользователем учебных переписок добавлен явный выбор DEMO-1.0. Текущая рубрика QA-ANSWER-1.0 оценивает загруженные ответы по всем проверяемым критериям, включая полноту ответа и инициативу в видимом контексте. Правила общения отделены от выполнения действий в CRM. Итог подписан «за загруженные ответы» и не выдаётся за оценку отсутствующей истории. Исходный признак полноты истории не меняется. Реальный учебный повторный разбор дал 30/20/20/20/10. Старые оценки не удаляются и сохраняют собственную версию рубрики.

Не реализованы: универсальный сбор истории всех мессенджеров, обработка звонков, обучение модели, проверка первоисточников и полномочий владельца базы, корпоративная авторизация и многопользовательское размещение.

Для рабочих переписок не хватает утверждённых условий компании. Готовый JSON-шаблон находится в `examples/company-kb.template.json`; все записи в нём черновые. Результаты на пяти учебных случаях не доказывают точность на реальных обращениях.

Запуск и работа описаны в README. Фактические прогоны ИИ следует фиксировать в файле 05 отдельно от результатов тестирования программы.
